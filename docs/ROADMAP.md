# 路线图

## v0.1 已完成

- 三道闸：入口扫描、解析净化、崩溃兜底
- 熔断（时间窗）+ 事件记录 + 通知
- 踹飞模式（一键让 LaTeX 插件失效）
- 毒公式指纹（只存哈希）
- 设置页 + 事件列表

## v0.2 计划

### 图片炸弹防护

Markdown 的 `![]()` 是另一条同样危险的链路：

- `data:image/png;base64,<几 MB>` —— 解码在 UI 线程，直接 ANR
- 远程图 8000x8000 —— 下载后解码，OOM
- 超长 URL（几十万字符）—— 解析器打嗝

做法：hook 图片加载前的 URL 处理，超过体积/尺寸上限就换成占位图。
需要处理的点比 LaTeX 多（可能有 Coil / Glide / 自研 loader 三种），所以放后。

### 渲染结果缓存

同一条消息在流式输出时会被反复解析（见 `docs/THREAT-MODEL.md` T7）。
把 `latex 源码哈希 -> Drawable` 做一层 LRU，命中就不重新构建。
难点是 Drawable 与 TextView 宽度的耦合，需要按宽度分桶。

### 代码块高亮限流

Prism4j 对超长代码块是 O(n)，一万行的代码块能把滚动卡死。
超过 300 行就关掉语法高亮，只留等宽字体。

### 按发送者记忆

同一发送者在本会话内触发 3 次熔断，之后他的消息一律纯文本。
需要 hook 消息模型（找到 senderId），会引入业务类依赖，得做版本适配。

## v0.3 想法

### 白名单

长按消息 → "这条允许渲染"。避免误杀真正的数学讨论。
技术上需要 hook 长按菜单，比较脏；替代方案是设置页里加一个"最近被拦的消息"列表，
点一下就把指纹加白。

### 规则热更新

危险宏的特征列表能从远程拉（用户手动点更新，不自动）。
好处是不发版也能跟上新玩法；坏处是引入了网络依赖，跟"不上传任何内容"的承诺要划清界限。

### 真实可见性

如果哪天能稳定拿到元宝派列表的适配器，再考虑做真正的"可视窗口统计"。
现在的代理指标已经够用，不值得为它冒兼容性风险。

## 不做

- **不拦截消息**：我们只影响自己这台手机怎么渲染，不改协议、不改服务端
- **不做通用 LaTeX 沙箱**：那是另一个项目，成本高一个量级
- **不上传数据**：一个字都不传
